# 0001 — `release` is the integration branch; `main` receives post-release sync PRs

- **Status**: accepted
- **Evidence**: `.github/workflows/ci.yml`, `release.yml` (`open-main-pr` job), `preview.yml`

## Context

The project ships from tagged releases and a daily-moving preview channel, and wants `main` to
always reflect the last published release rather than in-flight work.

## Decision

Day-to-day work lands on `release`. CI runs on pushes to `release` and PRs targeting
`release`/`main`. Tagging `v*` triggers `release.yml`, which tests, builds assets, publishes the
GitHub Release (notes generated by git-cliff), and then automatically opens a
`release` → `main` sync PR. `preview.yml` force-moves the `preview` tag daily and overwrites the
prerelease build.

## Consequences

- New branches and PRs should be based on / target `release`, not `main`.
- `main` may lag `release`; never treat `main` as the freshest code.
- The `preview` tag moves; it must never be used as a version baseline (see
  `conventions.md` § Versioning).
