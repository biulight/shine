# Preset 能力说明与代码信任边界 PRD

> 状态：已实施；本文规定当前开发分支的目标行为，是否发布以 CHANGELOG 和发行版本为准。
> 日期：2026-09-16。读者：负责实现、评审和验收的 Codex / 工程师。
> 本文为内部 PRD，不得发布到公共手册或网站。实施时另行更新中英文公共说明。

## 1. 背景与结论

当前 Shine 将结构化操作推导出的权限和作者填写的权限表合并到安全 Plan。
缺少声明、缺少已知能力以及审批后输入变化，可以阻止受保护的生命周期操作。
但 Shine 不分析任意脚本正文来证明声明完整，也不通过操作系统沙箱限制脚本行为。

仓库已有两个典型例子：

- [Surge 配置](../presets/app/surge/shine.toml) 在 `post_install.command` 中直接指定
  `surge-cli`，又在 `permissions.commands` 中重复声明。当前规划器可发现后者漏填。
- [usetproxy 脚本](../presets/shell/proxy/uset_proxy.sh) 内部调用 `yarn`，而
  [对应配置](../presets/shell/proxy/shine.toml) 只有空的版本化权限声明。
  当前检查不会由脚本正文发现遗漏；将 `curl` 写入脚本也不会自动产生网络或命令检查。

因此，精细的作者权限表并不构成任意代码的能力边界。继续要求穷举会增加维护成本，
并容易让用户误认为“未列出的操作不能发生”。

本次改为三个明确概念：

| 概念 | 信息来源 | 产品承诺 |
| --- | --- | --- |
| Shine 计划执行的操作 | Core 结构化模型、资源状态、归属记录 | 纳入精确审批和执行前复核；在已有执行器边界内受控 |
| 作者提供的能力说明 | 可选的 Preset 元数据 | 帮助审阅，未经代码完整性验证，不是运行时限制 |
| 未隔离代码及其信任 | Core 根据可执行入口自动识别；用户授权 | 明确告知执行任意代码的风险，并绑定适用的代码或开发来源 |

这里的“受控”不表示任意子进程内部行为都受控。例如直接执行 `surge-cli reload`，
Shine 知道启动哪个程序，但不能穷举或限制该程序及其后代的文件、网络等副作用。

## 2. 目标、范围与非目标

### 目标

1. 用户能区分“Shine 已知并计划的操作”和“作者声称代码会做的事”。
2. 静态文件和其他纯结构化 Preset 不再为了通过检查而填写空权限表或重复命令、路径。
3. 任意代码不会因作者少报、空报或不写权限表而隐藏其未隔离性质。
4. 保留快照审批、资源归属、环境输入身份、秘密敏感度、提权和恢复边界。
5. 所有前端、作者工具和导出报告使用同一套 Core 语义，不能仅修改 CLI 文案。

### 范围

- App 文件、生成器、生命周期钩子、artifact / teardown / refresh。
- Shell 脚本安装、更新和 profile 集成，包括 `needs_source`。
- Sys 受管资源、bootstrap 脚本、profile 可执行片段及现有包管理器入口。
- Plan、信任、校验、lint、脚手架、假设计划、fixtures、bundle 与文档。

### 非目标

- 不新增脚本 AST 分析、命令依赖扫描或通过执行脚本“探测权限”。
- 不新增系统沙箱、系统调用拦截、网络代理或通用命令白名单。
- 不承诺阻止恶意代码访问当前进程本来可访问的文件、环境或网络。
- 不新增任意代码回滚、逐次 Shell 命令审批或全局跨目标事务。
- 不借本次改动删除 Plan、信任、日志、receipt、归属或管理员授权机制。

## 3. 产品行为要求

### 3.1 自动推导已知操作

Core 从已有结构化模型推导受管文件、启动器、备份、manifest、journal、系统设置、
明确指定的命令和解释器等能力，作者不再在权限表中重复填写它们。

- 没有 `[permissions]` 或没有枚举 `commands/filesystem/network/system`，
  不再仅因声明缺失而阻止操作或信任登记。
- 直接配置 `post_install.command = "...surge-cli"` 时，Plan 自动列出该命令；
  删除重复的 `permissions.commands` 项不再造成缺少命令权限错误。
- 必要的结构化输入无效、目标无法确定、归属冲突、信任缺失等仍然阻止操作。
  不能把已有所有 `uncomputable` 或 `missing_declarations` 错误无差别删除。
- 已知命令只表示启动身份；不能将它描述成“仅允许执行此命令”或命令内部副作用边界。
- 纯静态复制不因文件扩展名为 `.sh` 就自动变成“本次执行代码”；分类依据是入口语义。

### 3.2 代码风险由 Core 判断

不再以作者是否填写 `opaque_code = "unrestricted"` 判断代码是否未隔离。

- App 的 script、generator、artifact、teardown 和任意 command 钩子均属于未隔离执行入口。
- Shell 被安装为命令的脚本，以及将被 source / eval 的内容，均属于代码交付入口。
- Sys 自定义脚本、可执行 profile 内容和分发脚本均属于未隔离代码。
- Core 固定包管理器适配器仍按已有来源策略运行，但审阅不得声称包管理器及其安装脚本
  的副作用完全受 Shine 约束；本次不为系统工具另建一套信任登记。
- 内置与外部代码具有相同的未隔离风险描述；内置来源沿用发行物信任，不能标记为“已沙箱化”。

分类必须跟随实际生命周期触发条件：没有触发 App 钩子的操作不请求该钩子的执行信任；
安装 Shell 命令显示“交付供以后运行的代码”，不显示为安装时已经执行。
真正不受本次变更影响、仅可用而未安装的 Preset 不应阻塞当前操作。未选中不等于不受影响：
共享资源变更所影响的已安装命令必须按 3.5.2 纳入审阅和信任检查。
保持完全 no-op 规则；共享代码被替换时，即使启动器本身未变，也不属于完全 no-op。

### 3.3 作者能力说明是可选信息

本次不新增一个强制作者维护的平行清单。继续读取 v1/v2 权限声明，以兼容已有 Preset。

- `commands`、`filesystem`、`network`、`system` 作为作者能力说明展示，
  不用于声称代码完整性，也不作为任意脚本执行白名单。
- 显式提供的旧字段仍做格式、版本、路径和重复项校验；“可选”不等于接受坏格式。
- `[permission_defaults]` 继续按目标解析，条目级声明替换默认声明，不合并到无关目标。
- `opaque_code = "unrestricted"` 继续接受，但成为兼容字段；省略它不会降低自动识别的风险。
- 空表、缺表、有枚举表对同一个代码入口产生相同的未隔离分类。
- 旧能力说明可保留，默认脚手架不再生成推测性清单、空表或要求穷举副作用的注释。
- `preset new --unrestricted` 保持可调用，作为兼容选项处理；不再意味着默认模板更受限。
  帮助文本说明所有任意代码均未隔离，不以每次运行的警告惩罚旧用法。

`environment` 与 `administrator` 不属于本节降为说明的字段，见下节。

### 3.4 保留有实际执行语义的约束

- 保留 Shine 管理的 env 映射、名称允许列表、秘密敏感度及输入身份绑定。
  需要注入这些输入的 Preset 仍需提供相应声明；没有输入则无需空权限表。
- 不能因省略权限表或使用旧 unrestricted 字段，自动注入整个配置环境或秘密集合。
- 保留现有 `requires_admin`、Administrator 能力、平台提权流程及显式授权检查。
  本次不改变管理员声明的现有要求，也不推断任意脚本是否会自行调用 `sudo`。
- 文案必须限定为“Shine 管理的注入/提权”。不能承诺阻止脚本读取继承环境、自己调用
  提权工具或利用既有系统凭据。本次不顺带改变环境继承策略。
- 受管资源的所有权、目标状态、保护路径、备份冲突和恢复检查保持有效。
- Plan 继续绑定代码、请求、已知能力、输入身份及现场状态；审批后变化必须重新审批。

### 3.5 外部代码授权与持久信任

不能仅移除声明检查，而保留“未写 unrestricted 就不需要 Shell 代码信任”的分支。

- 所有外部或 overlay 可执行入口，按目标和现有 capability 种类派生信任要求。
  外部 Shell 脚本无论权限表为空、缺失或枚举形式，都进入 `shell/<category>/<command>` 信任范围。
- 纯结构化数据操作不因缺表要求外部代码信任；现有内置来源策略保留。
- 默认信任仍绑定代码快照；用户显式申请的 development 模式仍绑定来源、层级、目标和能力。
  Preset 不得自行申请或生成任何信任授权。
- Snapshot grant 仅绑定 target、capability、完整类别摘要及其来源层；Development grant 绑定
  target、capability、来源根和层级。作者说明（包括 env/admin 声明）不单独参与 trust 匹配，
  仍进入 Plan 指纹和执行器检查。修改 metadata 字节仍使 snapshot grant 失配。
- 可信人工界面可一次确认当前 Plan 与列出的外部代码，仅授权本次操作，不写入 trust store。
  一次性授权只在进程内不可序列化的审批交接中携带精确代码身份；重新捕获来源或状态后复核。
- 自动化和普通 `--yes` 必须已有匹配 grant，不能冒充人工确认。只读/AI adapter 不能获得审批
  capability；AI 可生成、静态验证、请求审阅，但不能自行确认。无限制终端代理须由工具宿主限制。
- `info/update --run-generators` 未走统一人工审批，继续要求持久 grant；一次性生成使用交互式 refresh。
- snapshot 信任下，外部 Shell 应交付被审核的快照内容，不能通过指向可变源文件的链接，
  让登记后未审核的内容直接替换它。信任模式和部署模式的组合规则见 3.5.3。
- development 信任沿用其明确允许代码变化的语义；文案必须说明受信任来源代码可变化。
  两种模式都不承诺逐次拦截已安装命令、持续保护用户可修改的文件或防御本机同权限篡改。
- `trust grant preset` 仍是对当前目标的批量登记，不覆盖未来新增目标。

#### 3.5.1 信任摘要的文件边界

本次采用保守的完整类别快照边界，不依靠脚本依赖分析或作者清单裁剪摘要：

- App、Shell 分别绑定入口所属 `app/<category>/`、`shell/<category>/` 的完整有效快照；
  Sys 绑定所属 `sys/<os>/` 的完整有效快照，包括 profile 基础片段。
  结构化入口若还引用其他合法快照路径，其内容也必须进入边界；非法引用仍由校验拒绝。
- 从同一不可变 PresetSnapshot 派生登记、匹配、Plan 和实际交付所用的文件集合。
  摘要绑定确定性排序的逻辑路径、精确字节和每个文件的有效来源层级，涵盖文件新增、删除、
  重命名和内容变化；不包含物理 checkout 路径。development 的来源身份覆盖同一集合的
  来源根和层级，沿用显式允许同来源代码变化、来源根或层级变化需重审的规则。
- 无扩展名辅助文件、非内置脚本扩展名、数据文件、元数据和包清单/锁文件均不得因
  未列入 `permissions.filesystem` 或扩展名未知而从有效快照边界中剔除。
  保留现有快照采集对 `node_modules` 等内容的排除规则；不能因此将外部依赖描述为已绑定。
- 文件集合较大意味着同类别辅助文件或数据变化也会使 snapshot grant 失配，这是本次
  有意采用的保守策略。共享摘要不合并目标授权；每个目标/capability 仍需本次人工授权或独立 grant。
  文件纳入摘要也不等于将其分类为可执行入口，静态数据操作仍遵守 3.1 和 3.2。
- 此边界不证明脚本只依赖快照内文件，也不固定系统解释器、PATH 程序、运行时下载内容
  或其他外部资源。文案应描述为“绑定 Preset 有效快照”，不能承诺完整运行环境可复现。

#### 3.5.2 共享交付资源与受影响目标

本次保留 Shell 类别级共享快照部署，采用“扩大受影响目标审阅范围”的策略：

- Core 先根据计划写入/替换的共享快照、缓存和其他代码交付资源，以及现有 manifest/receipt
  推导受影响目标，再检查信任。检查集合包括本次选中且会发生代码交付的目标，以及依赖
  这些变更资源的所有已安装命令，不能只遍历命令行 selector。
- 对共享类别快照的替换，保守地纳入依赖该快照的所有已安装命令。每个外部/overlay
  目标都必须纳入本次人工代码确认或匹配持久 grant；未获授权时，在首次 mutation 前阻塞。
  为 A 重新登记不能替代 B 的授权，即使二者使用相同类别摘要。
- Plan 和审阅必须列明选中目标、连带受影响目标及共享资源关系，并绑定相关归属和现场
  状态；执行前重新计算并复核。继续遵守缺失来源、用户修改和恢复冲突规则。
  不因扩大审阅而创建未安装命令的启动器、运行其代码或隐式登记信任。
- 若所有相关资源都不变，则保留完全 no-op 行为，不因旧 grant 失配强制产生更新。
  新增的无关可用目标也不参与信任阻塞；实际交付的共享文件变化则按本节处理。

#### 3.5.3 信任模式与 Shell 部署模式

`TrustMode` 的 `snapshot` / `development` 与 `external_shell_mode` 的 `snapshot` / `live`
是两套独立设置。登记信任不修改部署设置，修改部署设置也不创建或转换 grant。
外部 Shell 的新安装或发生代码交付变更的更新遵守以下组合规则：

| 信任模式 | 部署模式 | 要求 |
| --- | --- | --- |
| 本次人工确认 | snapshot | 仅授权精确 Plan 和当前快照，不保存 grant |
| 本次人工确认 | live | 不足；必须已有 Development grant |
| snapshot | snapshot | 允许；交付匹配当前 grant 的捕获快照，源文件后续变化不进入已交付内容 |
| snapshot | live | 阻塞；不得创建指向可变来源或调用时读取可变来源的启动器 |
| development | snapshot | 允许；来源授权可覆盖后续代码变更，但部署内容仍只在明确安装/更新并审批后刷新 |
| development | live | 允许；明确告知以后运行/source 时可读取受信任来源的新内容，无逐次代码复核 |

“允许”仍以适用代码授权、Plan 审批、env/admin 契约和所有权等检查通过为前提。
Core 对不兼容组合返回稳定阻塞诊断；CLI 提示用户显式选择 snapshot 部署并重新计划，
或显式登记 development 信任。`--yes`、旧 unrestricted 字段和批量登记均不能自动代选。
规则覆盖原始脚本链接、Windows shim、Bun launcher、`needs_source` 和带 transforms 的
调用时渲染入口；不能仅修复 Unix 原始脚本链接。

升级 Shine 时保留已有 live 安装，不自动改写、禁用或删除启动器，也不自动补 development
授权。只读检查应对缺少新语义有效 development grant 的已安装 live 目标显示需要处理的
状态，说明旧入口仍可能读取变化后的源文件；完全 no-op 操作不据此新增 mutation 或阻塞。
下次实际安装/更新必须满足上表；卸载和显式恢复继续使用既有归属与恢复审批边界，不能
要求用户先信任代码才能移除旧入口。迁移提示不得声称旧安装已经受到持续运行时保护。

## 4. 审阅和命令体验

CLI 在原有计划审阅内按以下顺序显示信息，不增加第二轮重复确认：

1. **Shine 计划执行的操作**：实际文件和系统变更、已知命令启动身份。
2. **代码执行与信任**：目标、入口种类、立即执行或交付后运行、来源与信任状态。
3. **作者能力说明（未经验证）**：仅在作者提供时展示；长清单可放入详细输出。

存在未隔离代码时，默认输出必须包含实质边界提示，不能只藏在 `--verbose`：

> 此操作包含未隔离代码。代码运行时可使用其进程已有的系统权限；作者能力说明不是
> 文件、网络或命令访问限制。Shine 不验证说明是否覆盖脚本全部行为。

Shell 额外说明：

> 此处审核的是安装/更新代码。以后运行或 source 该命令时，Shine 不逐项拦截其行为。

development 信任说明代码变化可继续被该来源授权覆盖；内置来源说明依赖 Shine 发行物。
Shell 同时显示信任模式和部署模式，以及共享代码变更连带影响的已安装命令。
同一次批量审阅可以合并通用提示，但目标归属不能丢失。

- `--yes` 仅跳过原有确认，不隐藏风险，也不能创建缺失的持久信任授权。
- `validate` 成功只代表结构合法；`plan ready` 只代表当前假设下无已知阻塞。
  两者均不能显示“脚本权限完整”或“没有未声明行为”。
- lint 不再因正常代码天然未隔离就产生无法消除的质量警告；将该事实放入稳定风险字段
  和审阅文案。旧 `unrestricted_opaque_code` 警告退役，更新 `--deny-warnings` 用例。
- 对缺失 env/admin、无效结构和缺失信任保留具体补救提示，不统一建议补空权限表。

## 5. Core、接口和兼容性要求

### 5.1 语义分离

Core 必须分别保存、投影以下信息，不能让 CLI 根据字符串猜测：

- 已知计划能力：用于审批、执行前复核与现有结构化执行器契约。
- 作者能力说明：带明确来源的可选信息，不加入已知能力来冒充自动推导结果。
- 代码边界：目标、入口类别、执行/交付时机、未隔离状态和信任状态；Shell 另含部署模式
  及选中目标与共享资源连带受影响目标的区分和关系。

集合确定性排序、目标级归属与共享操作归属保持可验证。所有影响审阅的内容进入 Plan
指纹。导出仍禁止 argv、文件内容、环境值、秘密、物理 checkout 路径和原始错误。
本地 CLI 若需要更多细节，沿用现有受信任本地呈现边界。

### 5.2 版本与旧状态

- Preset TOML 继续接受现有元数据及权限声明 v1/v2；本次不强制批量改写用户源文件。
- Plan 和 Approval 的新语义升级到 schema v2；旧审批不可用于新执行。
- 信任 grant/store 使用 schema v2。已发布的 v1 记录保留、可查看与撤销，但标为需要按新边界
  重新审阅，不能静默当作新授权；此前未发布的 v2 草案直接由本模型替代。成功重新登记只替换
  相同目标/capability 的记录。
- 同时更新携带这些结构的 frontend projection、authoring report、fixture 和 schema 导出；
  变更其版本化公开形状时递增对应版本，并保留明确的旧版拒绝/读取规则。
- bundle manifest 和 pack report 升级到 v3，输出自动识别的代码风险与作者说明来源。
  旧 bundle 的 `unrestricted_opaque_code = false` 不能解释为无未隔离代码。
  如存在旧 bundle 消费路径，应从元数据重新分类；无法分类则报告未知并阻止自动信任。
- 不修改既有 Action IR / journal / receipt 格式来适配仅审阅层变化。
  恢复必须继续读取受支持的旧状态，并生成新 Plan 重新审批；不得复用历史 Approval。
- 不自动删除信任库、已安装命令或历史 journal，不自动运行迁移后的 Preset。

### 5.3 实施入口

优先阅读和调整以下模块群，最终文件拆分以仓库当前结构为准：

- `core/src/permission.rs`、`core/src/plan.rs`、`core/src/trust.rs`：声明、审阅、授权语义。
- `core/src/runtime/` 的 planner、trust、shell、validation、lint、pack、fixture、migration：
  统一分类和派生入口；移除声明缺失的旧阻塞时，检查迁移工具是否仍生成空表。
- `core/src/frontend/` 与 `cli/src/` 的生命周期和 trust 命令：安全投影、审阅、补救与确认。
- Preset 模板、内置配置、作者 fixtures、schema 快照、作者技能与两种语言的公共手册。

不要通过给每个 Preset 自动补 `opaque_code = "unrestricted"` 来实现本需求；
代码分类必须归 Core 所有，而非依赖作者自报。

## 7. 验收矩阵

| 场景 | 必须得到的结果 |
| --- | --- |
| 静态 App 复制，没有权限表 | 推导确切文件操作；不因缺表阻塞，不产生代码信任要求 |
| Surge hook 保留 command，删掉重复 commands 项 | 自动列出启动身份；标为未隔离入口，继续执行适用信任和审批检查 |
| 外部 usetproxy 无表、空表、只列 yarn、旧 unrestricted 四种配置 | 均识别为代码交付；均要求目标级代码授权，风险等级不因少报降低 |
| usetproxy 增加未声明 curl | 不声称检测到 curl；snapshot 信任因代码变化失配，development 按既有来源规则处理 |
| 已安装 Shell 快照后修改原始外部脚本 | 未审核内容不得通过可变源链接进入快照交付结果；更新需重新审核 |
| 入口不变，修改/新增/删除/重命名同类别无扩展名、非内置扩展名辅助文件或数据文件 | snapshot grant 失配；文件是否有 execute 声明不影响摘要覆盖；development 按 target/capability 和来源匹配 |
| 原始外部文件字节不变，仅改变有效来源层级 | snapshot 和 development 信任均需重审 |
| A、B 已安装且共享类别快照，B 内容变化后只重新登记并更新 A | Plan 列出受影响的 B；B 无本次人工授权或匹配 grant 时在首次 mutation 前阻塞，不替换共享树 |
| 上述共享更新中 A、B 均有匹配 grant，类别另有未安装的 C | 审阅后可更新共享树；不要求 C 的 grant，不创建 C 启动器或执行 C |
| snapshot 信任搭配 live 部署，含原始脚本和调用时 transforms | 安装/实际更新阻塞，--yes 无法绕过；提示显式切换部署或登记 development |
| development 信任搭配 snapshot 部署后修改来源代码 | 已交付内容保持原样；明确更新并审批后才刷新，不隐式改为 live |
| development 信任搭配 live 部署 | 明示未来调用可读取变化后的来源；不声称每次调用都经过快照复核 |
| 升级后已有 live 安装仅有旧 grant 或 snapshot grant | 保留入口，只读检查提示处理；完全 no-op 不阻塞，实际安装/更新按组合规则阻塞，允许按归属规则卸载 |
| 外部代码无持久 trust，人工确认 snapshot Plan | 仅授权当前操作与快照，不写 trust store；覆盖共享受影响目标 |
| AI/read-only adapter 请求审批或声明已确认 | 不产生审批 capability；工具宿主负责阻止不受限终端绕过 |
| 外部任意代码无信任，传 --yes | 仍阻塞；不得创建隐式持久信任 |
| 内置任意代码 | 呈现相同未隔离事实，沿用内置发行物来源信任 |
| 纯复制一个 .sh 文件且未注册执行入口 | 本次只呈现复制，不误报为已执行脚本 |
| env 映射来源未声明或秘密身份不可计算 | 仍阻塞，不回退为继承全部配置环境 |
| 受保护目标需要管理员授权但未满足 | 仍阻塞；作者说明和旧 unrestricted 均不能覆盖 |
| 旧信任 v1 | 可读取、列出与撤销；新执行前明确要求重审，不自动放大授权 |
| 作者说明改变，代码未变 | Plan 指纹变化；Development grant 不因说明变化失配；Snapshot 仍因 metadata 字节变化失配 |
| 审批后源代码、目标状态或 env 身份变化 | 原审批失效，无受保护 mutation 发生 |
| App hook 未触发、Shell 含共享资源在内完全 no-op、升级中的未安装目标 | 不凭无关代码新增执行/安装步骤或信任阻塞 |
| 外部 Shell 被 source | 审阅说明以后在用户 Shell 中运行，无逐命令拦截承诺 |
| pack、假设 plan、fixture 与真实 Plan | 同一元数据获得一致分类；作者报告没有执行授权或敏感值 |
| 旧 journal 的显式恢复 | 不删除旧证据；重新计划并审批，保留归属与冲突检查 |
| 修改 Preset 说明试图消除风险标志 | 自动分类保持不变，无法由作者字段关闭 |

测试以 InMemoryHost、结构化报告断言及隔离 CLI 用例为主，不靠运行真实越权脚本验收。
对 macOS、Linux、Windows 使用平台选择的合成 fixtures；标明未进行实机验证的边界。

实现验收至少覆盖相关 Core/CLI 测试、frontend conformance、信任兼容、完整快照摘要、
Shell 共享交付受影响目标、信任/部署模式四种组合、已有 live 安装迁移提示、元数据与作者
工具回归，运行格式检查和 clippy。调整公共文档后运行双语一致性、typecheck
与站点构建。变更 TypeScript 时才扩展相应 Bun 检查；遵守仓库隔离和工具版本规则。

最终交付报告必须明确：本版本改善的是审阅真实性、作者成本与信任入口一致性，
**没有新增阻止脚本内部未声明行为的运行时沙箱。**
