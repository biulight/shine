# GPG / age 混合收件人加密 PRD

> **状态：软件实现已完成，本机软件验收通过；硬件及其他平台待验收，尚未发布。** 日期：2026-09-08。

## 1. 背景与问题

同一团队可能同时存在使用 GPG / YubiKey 的成员，以及使用 age 普通 identity、Touch ID
或手机 identity 的成员。团队希望提交一份环境密文，每位被授权成员使用自己的工具和私钥
即可读取同一份秘密，无需统一私钥体系或维护两套环境文件。

当前 `shine.workspace.toml` 的 `[env.encryption]` 允许同时保存 `gpg_recipients` 和
`age_recipients`，但 `backend` 只选择其中一组。`secret::EncryptRecipients` 也只能表示
GPG 或 age。多个 recipients 目前仅代表同一种后端内的多个接收者。

当前实现依据：

- [密文路由与 recipients 类型](../cli/src/secret/mod.rs)。
- [工作区配置解析、封存、运行和缓存](../cli/src/env/workspace.rs)。
- [ADR 0008：按标签选择密文后端](kb/decisions/0008-age-secret-backend-tagged-ciphertext.md)。
- [Secrets 与 broker 不变量](kb/architecture/invariants.md#secrets)。

## 2. 产品目标与成功标准

1. 团队维护一个环境源文件，其中每个 payload 只有一份数据密文。
2. GPG 组或 age 组中的任一有效私钥持有者均能独立解密，得到完全相同的环境值。
3. 只读取秘密的成员只需自己的后端、identity 和必要插件，不要求安装另一种工具。
4. 明确启用混合模式才生成新格式；原有 GPG、age 配置及密文继续按原有语义工作。
5. 任一加密分支失败都不能生成缺少某组访问能力的“成功”结果。
6. `env run`、显式包含秘密的导出和 SSH broker 能消费新格式，保持既有秘密释放边界。

成功以第 11 节验收矩阵为准。性能、跨平台和硬件行为须通过实际验证，不能仅由代码路径推断。

## 3. 首版范围与非目标

首版提供工作区混合封存、所有现有统一解密入口对新格式的读取，以及必要的本机解密方式选择。
不增加 SOPS 运行时依赖，继续复用 GPG、age 外部工具及既有 identity 插件。

首版不包含：

- 双人批准、门限解密或必须同时提供 GPG 与 age 私钥的语义；本功能是任选一种。
- 两份完整明文分别加密后并排存储的方案。
- 全局默认混合加密、脱离工作区的 `env secret encrypt --backend hybrid`，或新的分组 CLI
  recipients 参数。独立 `encrypt` 仍支持现有 GPG / age；统一 `decrypt` 必须能读取新格式。
- 自动安装工具、自动导入或下载 GPG 公钥、自动创建私钥、修改硬件插件状态。
- 仅重包数据密钥而不重新加密数据的 recipients 更新命令。
- 自动迁移、历史 Git 密文撤销、上游 token 自动轮换。
- 混合模式编译缓存优化、整个多文件封存操作的全局事务、扩大既有平台支持范围。

## 4. 用户场景

| 角色 | 操作 | 预期结果 |
| --- | --- | --- |
| 项目维护者 | 配置两组公钥并封存 | 产生一份混合 payload，两组成员都可读取 |
| GPG 成员 | 运行工作区命令 | 仅使用 GPG 私钥，无需 age 工具或配置 |
| age 成员 | 运行工作区命令 | 仅使用 age identity，无需 GPG 工具或 keyring |
| 同时持有两种私钥的成员 | 读取混合 payload | 按本机明确选择调用一种后端，避免连续授权提示 |
| 修改秘密的成员 | 解开旧 payload，再重新封存 | 读取只需一种私钥，写入需要两种加密工具和全部公开 recipients |
| SSH broker 用户 | 远端请求已授权秘密 | 仍由本机批准和解密，远端不获得私钥或选择本机授权方式的权限 |

## 5. 配置与命令语义

### 5.1 显式启用

以下为配置形状；公钥均为占位示例：

```toml
version = 2

[env]
default_mode = "development"
files = [".env.shine.toml"]

[env.encryption]
backend = "hybrid"
gpg_recipients = ["<GPG fingerprint>"]
age_recipients = ["age1..."]
```

封存继续使用既有命令形状：

```bash
shine env secret seal --workspace shine.workspace.toml
shine env run --mode development -- <command>
```

两个列表同时存在不自动启用 `hybrid`。没有 `backend` 时仍遵循现有默认后端解析；显式
`gpg` 或 `age` 仍只使用对应列表。不得因新增功能改变这些已有合法配置。

### 5.2 recipients 与覆盖规则

- 混合模式要求工作区内两组 recipients 均存在，清理空白后各至少有一个有效项。
- 混合模式不从全局配置补齐缺失组，也不与全局列表合并，保证团队访问名单可从工作区审查。
- 混合封存的实际收件人必须受工作区声明约束。GPG 项使用完整公钥指纹，解析为本机已有的
  对应公钥及其有效加密子密钥；不接受本机 group 别名或依赖模糊用户 ID 匹配的访问名单。
  外部工具的配置、默认项或别名不得隐式增加或替换收件人，包括 GPG 的 `encrypt-to`、
  `hidden-encrypt-to` 和 group 展开。无法保证这一边界时，必须在解密旧 payload 前失败。
  此约束适用于混合封存的两种密钥封装，不改变既有单后端模式的配置语义。
- `seal --backend hybrid` 可显式选择混合模式，但仍必须找到工作区中的两组完整列表。
- 混合模式下拒绝未分组的 `-r/--recipient`，在解密或写入前说明应编辑工作区两组列表。
- 显式 `seal --backend gpg|age` 继续允许生成单后端密文，沿用既有 recipients 优先级；若
  工作区配置是 hybrid，状态输出应明确本次只面向所选组。不得把工具失败转换成此类覆盖。
- 全局 `secret_backend` 首版不接受 `hybrid`；对应错误应说明混合模式需要工作区访问名单。
- 没有 secret 且未配置任何加密策略的工作区继续无需 recipients；显式配置了 hybrid 的
  工作区仍需通过上述配置校验，不能将空文件当成无效策略已可用的证明。

### 5.3 本机解密方式

混合封装先由密文标签识别，再从封装实际包含的后端中选择一种解密方式。`secret_backend`
仍只影响加密，不能改变已有密文的解读方式。

首版使用仅从本机全局配置加载的 `hybrid_decrypt_backend = "gpg" | "age"`：

- 不允许项目配置、工作区文件、presets 或远端 broker 请求覆盖此设置。
- 仅适用于混合密文，不改变既有 GPG / age 密文路由，也不是新的秘密释放授权。
- 已明确选择时只尝试该后端；工具缺失、无匹配私钥、用户取消或解密失败均返回失败。
- 未设置时做不触发授权的能力预检。仅有一种候选时调用该种；两种都有时，在本机 TTY
  让用户选择本次操作使用的一种，非交互环境返回需配置选择的错误；没有候选时报告依赖缺口。
- “候选”只表示工具和必要 identity 配置可用，不保证持有可解密的私钥。不得为了探测
  可用性提前解密、触发 PIN / Touch ID / 手机确认，或扫描并输出私钥信息。
- 一旦调用所选后端，不自动因失败转试另一后端，不并行触发两种硬件授权。用户可修改
  本机选择后重新执行；取消当前操作必须终止当前解密。
- 本次选择可在同一次命令中复用，但不得缓存私钥、数据密钥、明文或硬件授权结果。

预检需要跳过与所选路径无关的 identity 检查：例如只使用 GPG 时，损坏的 age identity
路径不能阻止解密。broker 的选择和任何 TTY 交互均发生在本机，且必须在释放授权通过后。

## 6. 密文封装要求

### 6.1 单份数据与两种密钥封装

```text
secret payload 明文
        │
        │ 新生成的数据密钥 + 认证加密
        ▼
一份数据密文
        ├── 同一把数据密钥 → GPG 加密 → GPG recipients
        └── 同一把数据密钥 → age 加密 → age recipients
```

每次封存生成新的随机数据密钥，将序列化后的 payload 加密一次，再分别使用 GPG 和 age
封装同一把数据密钥。任一组解开密钥后，都必须验证同一份数据密文的认证信息后才返回明文。

外层继续以一个字符串保存在 `[payload].data`，不新增两份源文件或两套 secret key 列表。
新格式须使用独立、明确且带版本的标签。本文不冻结前缀拼写、二进制编码或具体字段布局。

### 6.2 实现前协议设计门槛

实现前必须通过新增 ADR 冻结以下内容，并提供可复现的协议测试向量：

- 成熟的认证加密算法及依赖库、操作系统随机源、密钥与 nonce 长度、生命周期和用量限制。
- 外层标签、版本、确定性编码、必需字段、未知字段处理、大小上限和重复字段拒绝规则。
- 数据密钥封装的类型、长度、版本及上下文校验；不得直接把任意后端明文当作有效数据密钥。
- 认证附加数据与完整性绑定范围：至少覆盖协议版本、算法、两个密钥封装及必要结构元数据，
  明确编码顺序，避免自引用。移除、替换或拼接任一封装都不能产生可被正常接受的修改版本。
- 密钥封装输出与适配器当前 UTF-8 返回接口的衔接：采用受限编码或字节接口，不丢失字节。
- 格式、依赖、私钥不可用、用户取消、工具失败和完整性失败的可诊断边界；无法可靠区分的
  外部工具错误必须保守终止，不能靠猜测 stderr 来触发回退。
- 混合封存的外部工具调用契约：冻结公钥解析规则、支持的工具版本、允许继承的配置及
  隐式收件人的禁用或拒绝机制，保证实际访问范围不超出第 5.2 节的声明。不能仅凭两次
  工具退出码为零认定名单约束成立，也不能通过修改用户的 GPG 配置或 keyring 达成隔离。

GPG 的额外收件人和 group 行为见
[官方收件人选项说明](https://www.gnupg.org/documentation/manuals/gnupg/GPG-Key-related-Options.html)。

不得使用自行实现的密码学原语。整体封装设计参考成熟的数据密钥封装模式，但不能把参考实现
等同于本协议已完成审计。可参考 [SOPS 加密协议](https://github.com/getsops/sops#6-encryption-protocol)。

### 6.3 完整性与威胁边界

- 解开数据密钥不等于解密成功；认证、payload 版本和 key 集合校验完成前不得释放明文。
- 拒绝未知版本、缺少任一分支、重复分支、非法长度、畸形编码及超出限制的输入。不得把
  已识别的新格式解析错误回退为未标记 GPG 或普通 age。
- 不在日志、argv、错误、审计或磁盘临时文件中写入明文数据密钥；保持已有秘密输出边界。
  密文临时文件继续私有创建，错误路径清理敏感缓冲区，不因失败而输出部分明文。
- recipient 公钥是访问名单，不是加密者签名。持有解密密钥的授权成员仍可读取、复制并重写
  秘密；本功能不证明作者身份，也不防止有权限者回放整个旧文件。
- 双后端提供两条独立访问路径，不叠加两种认证强度。任一获授权私钥泄露都可能暴露秘密。

## 7. 封存、迁移与失败行为

1. 捕获工作区的完整原始字节及摘要，从同一份不可变快照解析策略、源文件集合和两组
   recipients，并固定本次 CLI 参数。逐文件捕获源文件原始字节及摘要；在解密前完成策略、
   参数、公钥解析、隐式收件人约束和加密依赖预检。
2. 从捕获的源文件快照读取已有 payload，按其自身格式解密；混合格式采用第 5.3 节的
   本机选择，不重新读取另一版本的源文件。
3. 收集待封存值，生成新数据密钥和唯一数据密文，完成两种密钥封装及最终认证结构。
4. 两组都成功后，在内存中准备 `[secret]` 状态和 `[payload].data` 的更新。在每个文件
   原子替换之前，重新核对工作区完整字节和该源文件字节是否仍匹配捕获的快照。
5. 任一快照变化、文件消失或无法复核，均拒绝写入当前文件并终止本次封存，要求重试；
   不重新加载新名单后继续使用旧的封装结果。仅在复核通过后原子替换当前源文件。

上述复核包含等待 PIN / Touch ID / 手机授权期间的工作区修改，即使源文件没有变化，
recipients、backend 或源文件集合变化也必须拒绝写入。技术设计须冻结复核与原子替换之间的
并发控制方式及其保证边界，不能把彼此独立的摘要检查和 rename 当作无竞态的条件写入。

任一步失败或取消，Shine 不替换当前文件；无并发编辑时，其字节保持原样，包括原有明文
待封存项；存在并发编辑时保留外部修改，不用旧快照恢复文件。错误应说明 Shine 未更新该
文件，不能声称明文已被清除。前序已成功写入的其他文件不回滚，报告必须区分已完成、
失败和未处理文件；工作区策略变化后不得继续封存剩余文件。

旧 GPG / age payload 通过显式 `seal` 转成混合格式，转换者需能读取旧密文，并拥有两种
加密工具及全部公开 recipients。普通读取、`env run` 和配置加载不得迁移或改写源文件。

新增、删除 recipients 后重新封存使用新的数据密钥并重新加密数据。移除成员不撤销其对
历史版本的访问；已经暴露或需撤销的服务凭据仍需在上游轮换。

## 8. 运行、导出、缓存与 SSH broker

- 统一 secret 解密入口支持新格式，覆盖直接 decrypt、secret export、workspace export、
  `env run`、proxy、SSH 直接秘密注入和 broker；不能只在工作区内实现一套旁路。
- 直接 decrypt 的成功 stdout 必须保持明文字节精确，不附加换行或状态提示。
- workspace export 仍默认不解密，只有 `--include-secrets` 才释放秘密；包含秘密的文件
  保持既有私有创建要求，dry-run 不输出值。
- 首版在当前工作区加密策略为 hybrid，或本次 mode 实际消费的任一源文件包含混合 payload
  时，跳过整个编译结果的缓存读取和写入，直接编译源文件。该规则也覆盖工作区策略仍为
  `gpg` / `age`、通过 `seal --backend hybrid` 生成密文，以及只修改策略尚未重新封存的情况。
- 是否跳过缓存必须在任何缓存解密之前，由同一份捕获的工作区及源文件快照判断；随后从
  这些字节编译，不能检查标签后重新读取另一版本的源文件。已识别的混合格式即使畸形也
  不能改走缓存路径掩盖错误。未被本次 mode 消费的源文件不影响这一判断。
- 不删除旧缓存，不将混合源数据重新加密为单后端缓存，不因另一工具缺失重复警告。
  只有当前策略与本次消费的源文件均不涉及混合模式时，才保留既有单后端缓存行为。
- 因此混合 payload 的读取者不需要另一种加密工具，也不会因旧缓存改变本机选择或触发
  另一种硬件授权。若同一次命令还消费旧单后端 payload，仍需按各自标签满足其解密依赖。
  重复运行可能重复解密各源文件，性能和授权次数需要记录验证，但首版不通过持久化明文
  或降低授权要求优化。
- broker 继续校验完整 workspace/source 字节摘要、mode、release 和 argv 后再解密。
  远端不传数据密钥、本机解密偏好或可用于覆盖本机 identity 的字段。
- 修改名单、转换格式或重新封存会改变既有策略快照，按原规则重新审核；不得忽略新封装
  字段或放宽摘要匹配来复用旧授权。既有 direct 请求本机确认要求继续有效。

## 9. 兼容性与发布要求

- 新版本继续读取既有未标记 GPG 和 `age:` 密文，既有单后端写入格式保持不变。
- 外层封装有独立版本；原则上不改变工作区 v2、环境源 v1 和内部 secret payload 的语义。
  若技术设计发现必须调整其版本，应在实现前 ADR 中说明原因和兼容策略。
- 旧版本 Shine 无法读取混合格式。团队应先升级实际执行解密的机器和 broker 本机，再转换
  文件；不能承诺未升级客户端会显示专门的新格式错误。
- 只有显式封存或显式单后端覆盖才修改格式；升级安装、配置读取均不自动迁移。
- 实现同一 release change 必须同步英文手册和简体中文手册的配置、命令、环境指南、秘密
  安全指南及受影响 broker 说明；本 PRD 和 KB 不进入公共网站。
- 新增 ADR，并更新已有 Secrets 不变量和数据流：保留“密文自描述”的原则，明确本机选择
  仅在混合封装列出的方式之间生效，不得用加密默认值重新解释旧格式。

## 10. 实现影响与成本

| 工作项 | 主要位置 | 估算 |
| --- | --- | --- |
| 配置、参数与校验 | `cli/src/env/workspace.rs`、`cli/src/env/commands.rs`、config 和参数定义 | 1–2 人日 |
| 协议、封装、收件人约束和密钥生命周期 | `cli/src/secret/`、外部工具调用契约、密码学依赖、ADR 与协议向量 | 3–5 人日 |
| 本机选择、快照复核、缓存及调用方集成 | config load/save、env、文件写入、proxy、SSH broker | 2–4 人日 |
| 回归、平台验证与发布文档 | 测试、双语手册、KB | 2–4 人日 |

总计 **8–15 人日**，保留为初步估算，不是已验证排期；新增收件人约束、源格式驱动的缓存
跳过与并发控制成本须在技术设计冻结后复核。不含独立安全审计、硬件设备准备或外部插件
缺陷修复。若要求透明尝试所有后端、混合缓存或全局混合 encrypt，应重新估算。

建议交付顺序：先冻结 ADR 和协议向量，再完成 secret 模块及攻击性输入测试，随后接入工作区
和本机选择，最后验证所有秘密消费路径、硬件交互与发布文档。协议未审定前不产生正式可提交密文。

## 11. 验收矩阵

| 场景 | 必须满足的结果 |
| --- | --- |
| 两组配置、未指定 hybrid | 保持既有后端选择，不自动扩大接收者范围 |
| 显式 hybrid 缺一组 / 空组 / 配合 `-r` | 预先失败，不解密、不写入、不从全局补齐 |
| 混合名单使用 GPG group 别名或模糊用户 ID | 解密前拒绝，提示使用完整公钥指纹，不按本机别名展开 |
| GPG 配置含额外 recipient、encrypt-to、hidden-encrypt-to 或 group | 成功封存仅面向工作区声明的身份；未声明且无其他授权身份的密钥不能解密；无法约束时解密前失败 |
| 两种后端封存成功 | 一个 data payload，两组分别解密得到完全相同值 |
| 只装 GPG / 只装 age 的读取者 | `env run` 和允许的导出成功，不要求另一工具，不写混合缓存 |
| 单后端工作区策略 + CLI 封存为 hybrid，或混合密文尚未随策略变更重新封存 | 连续运行均跳过缓存读写，遵循本机解密选择，无另一后端的缓存加密或授权提示 |
| 消费混合源时存在旧单后端缓存，包括匹配输入摘要的缓存 | 在缓存解密前跳过，不因缓存可读而绕过混合源校验或本机选择 |
| 缓存判断后源文件变化 / 混合封装畸形 | 编译使用判断时同一份快照；畸形混合数据失败，不能用缓存掩盖 |
| 未消费的其他 mode 含混合源 / 策略及所消费源均为单后端 | 不因未消费的混合源禁用缓存；既有单后端缓存行为保持不变 |
| 两种候选都有，未选择 | 本机 TTY 选择；非交互可操作地报错，不同时启动后端 |
| 显式偏好的一侧缺工具或无私钥 | 明确失败，不自动换另一种方式 |
| GPG 路径旁有失效 age identity | 与本次路径无关的配置不阻断 GPG 解密 |
| PIN / Touch ID / 手机取消 | 终止，不触发另一方式、不释放秘密 |
| 任一加密工具或 recipient 失败 | 该文件字节原样保留，不生成单组成功结果 |
| 数据、版本、算法或密钥封装被替换 | 解析或认证失败，不能接受另一分支后释放明文 |
| 删除分支、重复字段、超大或畸形输入 | 受限地拒绝，不递归尝试、不启动不必要的外部命令 |
| 从另一文件拼接封装 | 完整性验证失败，不能产生两组读取不同内容的合法对象 |
| GPG、age 老密文读写 | 格式和明文保持兼容，包含换行的 stdout 字节精确 |
| 旧格式显式转 hybrid | 新密文双方可读；普通读取不迁移 |
| recipients 删除后重新封存 | 新密文拒绝被移除且无其他授权身份的成员，历史访问边界如实说明 |
| 封存期间源文件变化、消失或无法复核 | 替换前失败，保留并发编辑，不从旧快照恢复 |
| 等待硬件授权期间修改工作区 recipients、backend 或源文件集合，源文件不变 | 替换前失败，不按旧策略写入，不继续处理剩余文件 |
| 多文件封存期间策略变化或其他中途失败 | 已成功文件不回滚，当前文件不写入，准确报告已完成、失败和未处理文件 |
| 默认 export / dry-run | 不额外解密，不输出秘密值 |
| broker 未授权或快照变化 | 在解密前拒绝，原授权不可绕过 |
| broker 允许的新格式请求 | 本机选择和解密，仅释放审核通过的 keys，远端不接触私钥 |
| 错误、取消和异常退出路径 | 日志无秘密或数据密钥，无新增明文持久化、无部分成功 stdout |

协议单测和受控外部工具测试必须覆盖主要失败分支；使用隔离 keyring / identity 验证真实
GPG 与 age 跨组互操作。隔离 GPG 配置还须包含额外收件人和 group，验证实际加密结果的
访问范围；用受控同步点覆盖硬件等待后、替换前以及两个文件之间的快照变化，并覆盖技术
设计确定的并发控制边界。普通 GPG / age 路径覆盖现有支持的 macOS、Ubuntu、Windows 环境；
Touch ID 仅在 macOS 实测，手机与 GPG 硬件路径在现有支持组合实测。无法实测的组合必须
记录为未验证，不用模拟工具测试代替硬件验证结论。

## 13. 实施记录（2026-09-08）

- ADR 0084 固定 `hybrid:` 二进制 v1、XChaCha20-Poly1305、OS 随机数据密钥、
  nonce 绑定密钥记录、两份封装的 AAD 绑定、受限解析与可复现完整向量。
- 工作区双名单校验、GPG 完整指纹解析与精确加密键选择、忽略隐式收件人配置、
  两工具公开探针预检均在旧密文解密前进行。全局偏好仅用于混合读取，不自动回退。
- 运行路径以捕获的工作区和本 mode 源字节决定缓存跳过并编译；统一读取路径覆盖
  export、proxy、SSH 与 broker。broker 既有释放授权和快照验证保持在解密之前。
- 封存持有工作区与各源文件的协作锁；私有临时文件准备好后复核完整字节，再替换。
  失败保留外部编辑并报告完成、当前失败、未处理文件数量。
- **明确保证边界**：本方案不提供对不遵守锁的任意编辑器的文件系统 CAS。外部写入者
  在最后字节复核与 rename 间仍可竞争；封存时需排除这类写入。硬件等待阶段发生的
  编辑会在最终复核发现。此边界按第 7 节要求冻结，不声称摘要检查本身消除所有竞态。
- 实际硬件 PIN、Touch ID、手机授权、跨机 SSH，以及 Ubuntu/Windows 运行尚未验证。
  GnuPG 2.2–2.5 / age 1.x 是首版工具契约；具体实测版本与软件测试结果见后续验证记录。
